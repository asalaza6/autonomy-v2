# Agent Prompt Guide For This Repo

This directory contains the repo-local prompt contract for Autonomy V2's three
agent types:

- PM planning: `pm-agent`
- Implementation: `architecture-agent`
- Review and merge gating: `reviewer`

The active agent wiring lives in
`prompts/autonomous/v2/config/agents.json`. The scheduler reads that config,
loads each agent's `system.md`, and runs the packaged default runner against
this repository. The handoff files are optional continuity notes for humans and
future prompt updates; they are not the durable task queue.

Each `system.md` points agents at `prompts/autonomous/v2/project-context.md`.
That file is the editable project-specific context pack. Keep durable project
facts there instead of duplicating the same context across every prompt.

## Repo Contract

This repo is the `autonomy-v2` package and hosted control-plane app.

Current branch contract:

- integration branch: `dev`
- production branch: `main`
- blocked direct targets: `main`, `master`
- merge strategy: merge commits into `dev`
- sprint id: `multi-agent-mvp`

Current deployment contract:

- deploy means fast-forwarding `main` from `dev`
- after `main` is updated, this repo runs `git push heroku main`
- the hosted control plane is served by `autonomy-v2-control`

Current verification contract:

- implementation work must pass `npm run typecheck`
- tests should be added or run when the task changes behavior, especially
  control-plane, deploy, runner, queue, or sync behavior

## PM Agent

Prompt files:

- `pm-agent/system.md`
- `pm-agent/handoff.md`

Config identity:

- id: `pm-agent`
- role: `pm`
- queue: `prompts/autonomous/v2/queues/pm-agent.json`
- git author: `autonomy-pm[bot]`

The PM agent turns a submitted PRD into implementation-lane tasks. In this repo
there is currently one implementation lane, `architecture-agent`, so most PRDs
become one scoped architecture-agent task unless the request clearly needs
separate steps.

The PM agent should:

- read the PRD request and requirements
- create concrete acceptance criteria
- assign tasks only to configured implementation agents
- target all automation at `dev`
- keep work narrow enough for review and recovery

The PM agent must not:

- write feature code
- merge PRs
- target `main` or `master`
- invent unconfigured agent ids

Good PM output for this repo names the files or subsystems likely to change,
states how the behavior should be verified, and keeps the task useful if it is
later reconstructed from tracked queue state.

## Implementation Agent

Prompt files:

- `architecture-agent/system.md`
- `architecture-agent/handoff.md`

Config identity:

- id: `architecture-agent`
- role: `implementation`
- queue: `prompts/autonomous/v2/queues/architecture-agent.json`
- scope: `**/*`
- required checks: `npm run typecheck`
- git author: `autonomy-architecture[bot]`
- PR label: `agent:architecture`

The architecture agent is this repo's only implementation lane. It owns the
whole tree by scope, but it should still keep diffs focused on the assigned
task. It works in deterministic worktrees and lane branches generated by the
runtime, then publishes one PR for the completed lane.

The implementation agent should:

- read the current tracked queue task and acceptance criteria
- inspect existing code and tests before editing
- follow the package's existing TypeScript, CLI, server, and test patterns
- update focused tests or docs when behavior changes
- run `npm run typecheck` before publishing
- use stronger focused tests when touching deploy, control-plane, sync, runner,
  queue, review, or Git behavior

The implementation agent must not:

- merge directly to `dev`
- deploy or push `main`
- bypass required checks
- make broad cleanup unrelated to the task
- edit outside the assigned task's real scope just because `**/*` is allowed

For this repo, implementation changes commonly touch:

- `src/autonomy-v2/commands/` for CLI and git-backed commands
- `src/server/control-plane/` for manager, bridge, and hosted UI/API behavior
- `src/autonomy-v2/control-plane/` for status snapshots and summaries
- `src/sync/` for tracked PRD, queue, branch, and GitHub state reconstruction
- `tests/unit/` and `tests/smoke/` for focused coverage
- `prompts/autonomous/v2/config/` for repo-local agent and control-plane wiring

## Reviewer Agent

Prompt files:

- `reviewer/system.md`
- `reviewer/handoff.md`

Config identity:

- id: `reviewer`
- role: `review`
- queue: `prompts/autonomous/v2/queues/reviewer.json`
- git author: `autonomy-reviewer[bot]`
- comment signature: `reviewer-agent`

The reviewer agent gates implementation PRs and merges approved changes into
`dev`. It should review the lane diff against `origin/dev`, combine Codex review
judgment with deterministic wrapper results, and treat required-check failures
as blocking.

The reviewer should prioritize:

1. behavioral regressions
2. scope violations
3. missing or weak verification
4. merge safety
5. maintainability issues that materially affect delivery

The reviewer should approve when:

- the task acceptance criteria are met
- required checks passed
- the diff is scoped to the assigned work
- no blocking regression, deploy risk, or data-loss risk is present

The reviewer should request changes when:

- acceptance criteria are incomplete
- the PR cannot pass required checks
- the diff changes unrelated behavior
- manager, bridge, deploy, queue, sync, or runner behavior is changed without
  enough verification
- the branch cannot merge safely into `dev`

The reviewer must not:

- implement feature changes while reviewing
- review its own authored work as the gate
- merge into `main` or `master`
- ignore missing required checks

When changes are requested, the runtime creates a lane-local `review_followup`
task for `architecture-agent`. The follow-up should use the reviewer summary as
acceptance criteria unless the task already has more specific acceptance text.

## Prompt Maintenance

When changing these prompts, keep the three layers aligned:

- `system.md` defines durable agent behavior
- `project-context.md` defines editable project-specific context
- `handoff.md` captures short-lived operational context
- `config/agents.json` defines which prompt file, queue, role, scope, checks,
  labels, and git identity the runtime actually uses

After changing prompts or config, run at least:

```bash
npm run typecheck
```

Run focused tests too when the prompt/config change depends on runtime behavior
rather than wording only.
